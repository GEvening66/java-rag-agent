# 第 5 课笔记：评测闭环优化

## 评测闭环 v1 → v2
- **v1（第 3 课）**：只测检索层 —— recall@k = "答案块进没进候选"
- **v2（本课）**：测生成层 —— 端到端 = "回答到底对不对"
- **诊断逻辑**：
  - recall 高 + 端到端低 → 问题在生成/prompt/引用环节
  - recall 低 → 问题在检索环节（切分/embedding/k）
- 这就是"评测驱动优化"：先用数据定位是哪一环，再动手改

## 三个新指标
1. **端到端正确率**（fact/multi）：模型最终回答是否正确（LLM-as-judge 判）
2. **拒答率**（no_answer）：该说"资料中没有"时说"没有"的比例 —— 防幻觉的最终防线
3. **忠实度**：回答有没有编造（4a 的引用校验结果可以当作它的近似）

## LLM-as-judge（本课核心工具）
- **为什么**：人工判 22 题累且主观；让模型当裁判判另一个模型的输出，可批量自动化
- **局限（面试必讲）**：
  1. 裁判模型可能误判（自评偏差）→ 必须**抽样人工复核**
  2. judge 的成本和延迟 → 评测集规模要权衡
  3. 裁判 prompt 本身要设计（给标准答案、允许同义表述）
- 面试口径："LLM-as-judge 是 agent 评测标配，但我知道它的局限——所以我会抽样人工复核"

## 优化三板斧（5b 预告）
1. **数据清洗**：过滤 URL/参考链接/乱码块（第 3 课 #65 的教训）——治本
2. **k 实验**：k=1/3/5/7 对比 recall + 成本，画一张表
3. **重排 rerank**：粗召回 top-20 → 精排取 top-3（工业标准做法）

## 成本统计（5c 预告）
- 一次问答的成本 = embedding（每块）+ 生成（token）+ judge（如果评测）
- 面试官必问："你的系统跑一次多少钱？"——要有数

## 5.5 深度冲刺：工具调用升级（08_tool_agent.py）
### 为什么硬编码检索不算 agent
硬编码 = 程序写死"先检索再回答"，模型没有选择权。
工具调用 = 把检索注册成工具，模型**自己决定**要不要检索、检索什么、检索几次。
**这是"RAG 应用"和"agent 应用"的分界线。**

### function calling 协议三件套（面试必背）
1. `tools`：声明可用工具（name / description / parameters）
2. `tool_calls`：模型回复"我要调用 XX，参数 YY"（消息里附在 assistant 消息上）
3. `role=tool`：程序执行完工具，把结果作为 tool 消息回传，模型继续思考
- 循环直到模型不再调用工具，或达到 MAX_STEPS（有界！）

### 面试口径（5.5）
1. "你的 agent 怎么调用工具？" → 协议三件套讲一遍
2. "怎么扩展新工具？" → 工具注册表加一条：实现函数 + TOOLS 里登记（name/description/参数）
3. "工具调用失败怎么办？" → 把错误信息作为工具结果返回，模型看到会自行处理；
   生产里还要加超时、重试、trace
4. "和 MCP 什么关系？" → MCP 是工具调用的标准化协议（hello-agents 第 13 章），
   这里是手写最简版；懂原理后上 MCP 就是配置的事
5. "agent 可观测性" → 打印每一步"模型调用了什么工具、参数是什么、结果多长"——
   生产里用 trace 系统（Langfuse 等）做同样的事

## 5b：数据清洗 + 成本统计
### 数据清洗（01_chunk.py 的 clean_text）
- 目标：去掉 URL 链接行和 percent-encoded 乱码行（第 3 课 #65 的教训——
  它们不该进知识库，却参与检索竞争）
- 规则：行内无 "http" 且 '%' 比例 < 10%
- 改完要**删掉 cache/ 目录**重新向量化（缓存不失效的话清洗不生效！）
- 验证：重跑 03_eval（recall 应保持 100%），用 03_debug 看 volatile 的
  top-5 里 URL 块消失
### 成本统计（09_cost.py）
- 面试必问："跑一次问答多少钱？"
- 口径：token 数（API 返回 usage）+ 单价估算；embedding 免费；
  真实问答还有工具调用等 token，这是最小口径
- DeepSeek 价格近似：输入 ¥2/百万，输出 ¥8/百万（以官网为准）
### 面试口径（5b）
1. "知识库怎么保证干净？" → 切分前 clean_text 过滤 URL/乱码 + 评测发现脏数据的故事
2. "跑一次多少钱？" → 平均约 X 元/次，拆解输入/输出 token 构成
3. "怎么降本？" → 缓存、模型路由（简单问题用便宜模型）、控制 k 和上下文长度

## 5b 实测记录（2025）
- clean_text 清洗后 recall@3：**94% → 100%**（URL 乱码块消失，volatile 答案块升到第 3 名）
  ——数据清洗带来可量化收益，k 可以降回 3（省成本）
- 清洗后向量库块数减少（URL/参考链接行被过滤）
- 成本：平均每次问答 ≈ ¥0.0047（0.47 分钱，最小口径），
  单题 0.002~0.008 元，输出 token 是成本大头
